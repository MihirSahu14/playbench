# Game Studio Plugin v1: Design Spec

**Date:** 2026-10-13
**Working name:** `game-studio` (Claude Code plugin)
**Research:** [studio pipeline notes](../../research/2026-10-13-studio-pipeline.md)

## Goal
A Claude Code plugin that takes a solo dev or small team through the pipeline a game studio uses: discussion → idea → design → balance → art → dev → AI playtesting → deployment. Claude plays the studio roles, and the human makes every gate decision. v1 covers the front half, from the first discussion to a living GDD.

## Decisions
| Decision | Choice | Why |
|---|---|---|
| Audience | Solo dev / small team, author first | Simplest to build; can be published later without a rewrite |
| Engine | Engine-agnostic | Design docs don't depend on the engine; the dev step asks for the engine per game |
| v1 scope | `ideate` → `concept` → `greenlight` → `gdd` | Matches "start from discussions", and every later phase depends on these |
| Playtesting | After the game is built; AI agents play the real build | Playtesting needs a playable game, so it is not in v1 |
| Deployment | Its own phase, specific to each platform | Each store has different uploads, page setup and requirements |
| State | Plain markdown in the game's `design/` folder | Diffs cleanly in git and needs no database |

## Full roadmap
| Version | Steps | Notes |
|---|---|---|
| **v1** | `ideate`, `concept`, `greenlight`, `gdd` | This spec |
| v2 | `balance`, `art-bible`, `sprites` | Balance: cost curves, CSV sheets, Python Monte Carlo sims that read the GDD tuning knobs. Sprites: animation list, placeholder sprites, Aseprite CLI export scripts |
| v3 | `tech-design`, `dev` | Backlog, milestones, engine-specific code. **Requirement:** the build exposes its game state (a debug JSON dump or a hook into the game loop) and supports scripted input, so v4 can play it |
| v4 | `playtest` (**crucial**) | AI player personas (Newbie, Min-maxer, Explorer, Quitter) play the real build as separate subagents, using the game state, screenshots and scripted input from v3. They report confusion, boredom, exploits, dead ends, quit points and pillar violations, ranked by severity and linked to GDD systems. Batch bot runs collect telemetry for `balance`. Human playtests are still required to judge fun |
| v5 | `deploy` | Asks for the platform per game. **itch.io:** project page copy, page theme customization (colors, background, fonts, banner, plus custom CSS where the account allows it), screenshots and GIFs, uploads with the `butler` CLI, devlogs. **Steam:** store page copy, capsule art checklist at the required sizes, SteamPipe build upload config, achievements, release checklist. **Web:** builds for GitHub Pages / Netlify. Mobile stores later. Also covers launch checklists and store copy |
| v6 | `postmortem` | Patch plans and a "went right / went wrong" retrospective |

Each version gets its own spec → plan → build cycle.

## Plugin layout (this repo, v1)
```

skills/
  ideate/SKILL.md      ideate/template.md
  concept/SKILL.md     concept/template.md
  greenlight/SKILL.md  greenlight/template.md
  gdd/SKILL.md         gdd/system-template.md   gdd/index-template.md
examples/<sample-game>/design/   generated by the end-to-end dry run
docs/research/  docs/superpowers/specs/
```

## Output in the user's game folder
```
design/
  00-ideas.md        written by ideate
  01-concept.md      written by concept
  02-greenlight.md   written by greenlight
  gdd/index.md       written by gdd
  gdd/<system>.md    written by gdd, one per system
  decisions.md       every step appends: date | step | decision | why
```

## Shared rules (every skill)
1. **Input check:** read the previous step's file. If it is missing, stop and say which step to run first and which file is missing. `ideate` has no input.
2. **Gate check:** if the previous file's gate checklist is not fully ticked, warn the user and ask whether to continue. Never block.
3. **One question at a time** in conversation with the user, and prefer multiple-choice questions.
4. **Output:** write the step's file from its template. The file ends with a `## Gate` checklist, and every box starts unticked.
5. **Claude never ticks a gate box.** Only the user ticks them, either by editing the file or by telling Claude to tick a specific box.
6. **Re-run:** update the file in place and keep earlier content under `## History` instead of deleting it. Append a line to `decisions.md`.

## Steps

### ideate (studio ideation)
- **Discussion:** ask one at a time about games the user loves, target platform (itch, Steam, web, mobile), weekly hours and deadline, solo or team, and any must-haves or must-avoids.
- Generate 10–15 one-line hooks that vary genre and twist.
- Critique the top 5 with Schell's lenses (Essential Experience, Surprise, Fun, Problem Solving) and check each against the time budget.
- The user picks one hook.
- **Writes `00-ideas.md`:** the discussion answers, every hook, the critiques, and the pick.
- **Gate:** one chosen hook · a named target player · "why me, why now" answered.

### concept (studio concept)
- **Input:** `00-ideas.md`.
- Define 3 design pillars (each one a sentence that can be used to reject features).
- Core loop at 3 scales: 30-second, 5-minute and session, drawn as a text diagram.
- 3–5 comparable games, each with "take this" and "avoid this".
- **Writes `01-concept.md`:** pillars, loops, comparables, and a Librande-style one-page summary.
- **Gate:** pillars agreed · core loop stated in one sentence · comparables listed.

### greenlight (studio pitch / greenlight)
- **Input:** `01-concept.md`.
- Feature list split into must / should / cut. Estimate weeks for the must list using the hours from `00-ideas.md`.
- **Risk register:** fun, tech, art, scope and platform risks. For each: likelihood, impact, and the cheapest test that would retire it.
- **Skeptical publisher pass:** the strongest case for KILL, then a recommendation of GO or KILL.
- **Writes `02-greenlight.md`.**
- **Gate:** the user writes `Decision: GO` or `Decision: KILL` themselves. On KILL, keep the file and point the user back to `ideate`.

### gdd (pre-production, living GDD)
- **Input:** `01-concept.md` and `02-greenlight.md` (`Decision: GO` expected; otherwise follow shared rule 2).
- Break the must and should features into systems.
- **One page per system:** purpose (which pillar it serves), rules, inputs/outputs, tuning knobs (name, starting value, range; v2 `balance` and v4 `playtest` read these), and open questions.
- `index.md` lists the systems and their dependencies (a text diagram).
- Supports `gdd <system>` to create or update a single system page.
- **Gate:** every must-have feature maps to a system · no system has an empty rules section · open questions are listed or marked as none.

## Errors
| Situation | Behavior |
|---|---|
| Previous file missing | Stop and say: "Run `<step>` first; `<file>` not found." |
| Previous gate unticked | Warn, list the unticked boxes, and ask whether to continue |
| `design/` folder missing | Create it (only `ideate` needs to) |
| Re-run of a step | Update in place, keep the old content under `## History`, log the change in `decisions.md` |

## Testing
1. **Validation:** the manifest and every `SKILL.md` frontmatter parse (`claude plugin validate`, if available; otherwise a short script).
2. **End-to-end dry run:** install the plugin locally and run all 4 steps on one sample game. Commit the output to `examples/<sample-game>/design/`; it serves as both the test and the demo.
3. **Skill review:** check each `SKILL.md` against the `writing-skills` guidance.

## Success criteria
- From an empty folder, a user goes from "I want to make a game" to `design/gdd/` with all four gates ready for them to tick, without leaving Claude Code.
- Every file is readable on its own in plain markdown.
- No step ever ticks a gate box itself.
